# 工具审查

判断工具是否通过合理的接口提供了可信、代价可接受的能力。

## 确认依据与范围

确认任务目标、职责边界、建议接口、验收主张和待审版本。分别标明代码比较的 base/head，以及用于比较精度和性能的基线；基线位于其他分支时也应固定其版本。

以变更为起点，沿必要调用关系检查上下游。发现影响交付的既有问题时，说明归属和影响，不顺手扩大修复范围。

默认只读审查，不修改待审代码、索引、HEAD 或分支状态，也不自动发布外部评论。可以在项目允许的环境中运行检查或在隔离位置补充必要复现；证据缺口本身可以形成审查结论，不自动扩大为补实现、补全测试或重跑全部实验。

## 检查内容

- **实际调用与 API：**从正常使用场景检查接口是否够用、是否暴露多余能力，是否符合建议设计，偏离是否有充分理由。检查测试或视觉辅助的便利需求是否推动了不必要的公开接口。
- **职责与机制：**沿主要调用链检查职责、依赖、信息来源和相关公式、量纲、坐标或时间关系，确认程序实现了要求的能力。测试和指标通过不能替代这项判断。
- **输出正确性：**检查关键条件下的公开结果、无效或失败结果的含义，以及判断正确的依据。基线一致、测试数量和通过率都不能单独证明正确。
- **性能与行为：**检查分条件的耗时和精度、相对基线的变化，以及状态和副作用对结果的影响。核对运行条件和计时口径，不仅看总体平均值。
- **辅助代码与文档：**核对测试、夹具和视觉工具的组织、真实调用路径及依赖，以及文档修改是否符合 skill 入口中的共同要求。视觉审查入口要能使用被审能力；人工检查不能证明未覆盖的条件。

可以深入内部测试确认保障机制，但向用户汇报时围绕能力和结果组织，概括这些测试证明了什么，不逐条复述内部断言。

数值问题按承诺范围、精度或判定语义、可达条件及后果判断。不能因为问题位于边界就忽略，也不能因为容易构造反例就自动提高严重程度。不得擅自扩大支持范围、收紧精度承诺或放宽判定条件。发现局部问题后，仍应完成其他主要维度的判断。

## 交付审查结果

报告简短，但必须包含：

- **能力与使用判断：**实际提供什么、正常怎样调用，API 和职责是否合理。
- **行为与性能结论：**关键条件下的正确性依据、相对基线的变化，以及相关状态和副作用。
- **需要处理的问题：**触发条件、实际影响、证据位置及修改方向。
- **证据缺口与接受条件：**哪些主张尚未证明，是否影响本次接受；附必要的验证和视觉审查入口。

区分亲自复现、复核已有结果、静态判断和推测。不适用的维度简要说明理由，不虚构结果。“未发现问题”不能替代主要维度的结论。已有报告和测试输出可以引用，不重复粘贴内部细节。
