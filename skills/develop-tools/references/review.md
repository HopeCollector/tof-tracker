# 工具审查

## 读取任务依据

直接读取工单、相关聊天和后续确认记录，确认：

- 本次应提供什么能力。
- 建议接口和职责边界是什么。
- 哪些输入、输出和性能要求已经明确。
- 代码比较使用哪个 base/head。
- 精度和性能比较使用哪个基线版本。

查不到依据时说明缺口，不凭记忆补全。

## 审查权限

- 默认只读，不修改待审代码。
- 不改变待审工作区的索引、HEAD 或分支状态。
- 不自动发布外部评论。
- 可以在允许的环境中运行检查，或在隔离位置做必要复现。
- 缺少证据可以形成审查结论，不自动扩大为补实现或补齐全部测试。

## 检查内容

### 正常调用与接口

从实际使用场景检查接口是否够用、有无多余公开能力，以及是否符合建议设计。偏离设计时，检查理由和影响。

### 职责与实现机制

沿主要调用链检查职责、依赖、信息来源和计算关系，确认程序仍在完成要求的事情。

### 最终结果

查看不同重要条件下的输出，以及判断它正确的依据。必要时深入内部检查，但向用户概括这些检查保障了什么。

### 性能、状态和副作用

检查误差与耗时的分条件结果、基线对比和测量口径。存在状态时，检查状态变化是否影响后续结果；检查相关副作用。

### 辅助代码与文档

检查测试、夹具和视觉辅助的归属及依赖，核对文档是否符合项目 AGENTS 的共同要求。

## 数值边界如何判断

分别确认：

1. 输入是否位于约定支持范围。
2. 结果是否违反精度或判定规则。
3. 该情况能否在实际调用中出现。
4. 最终会造成什么行为和后果。

边界情况不能自动忽略，也不能仅因容易构造反例而提高严重程度。

不自行扩大支持范围、收紧误差要求或放宽判定条件。发现局部问题后，仍需完成其他主要维度的审查。

## 向用户报告

报告说明：

- 工具实际提供什么能力，正常怎样使用。
- API 和职责是否合理。
- 关键条件下的输出、误差、耗时及基线变化。
- 需要处理的问题、触发条件、影响和证据。
- 尚未证明的部分，以及它是否影响接受。

区分亲自复现、复核已有结果、静态判断和推测。“未发现问题”不能替代这些结论。
