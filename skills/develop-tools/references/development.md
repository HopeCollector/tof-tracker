# 工具开发

## 确认职责及建议接口

任务发起方在委派前给出明确的接口设计建议，让执行对话有具体依据。建议至少说明：

- 正常调用场景与主要调用关系。
- 建议公开的函数、类或方法。
- 输入输出、必要语义及生命周期。
- 一段最小调用示例。

用户直接发起任务时，先根据已有需求整理接口建议，对关键缺口向用户确认。不要让实现依赖未说明的接口假设。

检查建议是否足以完成任务。缺失或存在关键矛盾时，提出具体方案并对齐。实现细节可以自主完善；影响职责或正常调用方式的调整应显式说明，超出已有授权时先确认。

## 按职责实现

实现本次能力所需的最小范围，不顺手加入下一阶段功能。检查主要调用链、信息来源和相关公式，确认实现表达了任务要求的机制。

按 skill 入口中的共同要求组织公开 API、内部实现、测试夹具和视觉辅助；不要在辅助代码中维护另一套核心实现作为被测结果的替代品。

## 准备结果与性能证据

验证与承诺相称的典型条件、重要边界及失败情况，重点检查最终公开输出及其含义。根据主张选择解析情况、独立实现、独立几何或其他适当依据。

存在约定基线时，给出分条件的精度和速度对比。性能结果说明影响结论的输入规模、设备和计时范围；必要时区分初始化、更新、查询及传输。没有基线时不自行替换比较对象，仍需给出正确性和基本性能依据。

涉及状态时，验证相关状态转移、缓存失效、重复调用和重置行为，并检查输入修改、共享资源及资源生命周期等相关副作用。不为无关维度机械增加测试。

## 提供实际使用入口

准备能运行的最小例子，展示输入、输出和主要调用关系。

任务包含视觉审查工具时，让它实际调用本工具，文件集中、依赖清楚。需要内部数据时用夹具支撑，不因此扩大正式 API。人工点选结果不替代系统性正确性证据。

按共同要求完成必要的文档调整，不将交付流水或日常测试结果追加到使用说明中。

## 形成可审查交付

完成必要验证，并在已有委派授权内安排独立审查；授权未覆盖时，先将具体审查安排交给用户确认。修复问题后，验证受影响的主张，不无故重复全部检查。

独立审查者依据任务、代码和原始证据作判断，不将开发者的结论直接当作已验证事实。

直接向用户交付实现、最小调用、输入输出、验证证据和已知限制。完成提交、推送并提出 PR，供用户审阅；不自动合并。
