# 实际地图的独立几何审查

> 历史探索归档：源提交 `d4909aa2e0d87f60027a86b9856bdce534ca89e7`，原路径 `experiments/adaptive_distance_eval/REAL_MAP_REVIEW.md`。正文中的“当前”和版本判断限于原实验日期；不代表正式后端已具备该能力。

本审查确认真实 500 柱资产、闭合并集适配和距离 oracle 可用于本轮比较，**不据此判定 SdfLib 场、原始采样修复或优化结果通过**。几何验证在 CPU Docker 中执行；没有并发运行 GPU 或完整建场。审查者也是 `real_map_geometry.py` 的实现者，这里的“独立”指使用与 SdfLib、插值场及导出三角化不同的数值依据，并不代表几何代码经过另一位作者实现。

## 并集与地面的几何语义

适配器只接受八顶点、十二三角面的轴对齐闭合盒和完整的 `z=0` 矩形地面；同时检查六个面的位置、朝向及面积。它不是任意 mesh 的布尔运算器。原地图保留 500 根柱子、4000 个障碍顶点、6000 个障碍三角面，以及独立地面的 4 顶点、2 三角面；正体积重叠共有 **52 对**。

并集边界用轴对齐矩形相减构造：删除被其他实体覆盖的面，去掉重复共面区域，再按所有共线角点切开边，使用矩形中心扇形三角化，避免 T 形接点留下未匹配网格边。输入的重叠没有变成独立障碍的最小 SDF；占据内部距离测量到的是并集外露边界。

源地面是开放、有限的薄片，本身没有固体内部符号。为满足闭合实体查询，适配明确增加了覆盖查询 cube 的闭合 ground slab。cube 为 `(-51.2,-51.2,-43.7)` 到 `(51.2,51.2,58.7) m`；slab 的侧面和底面离 cube 至少 `119.90016820845966 m`。对 cube 内任一点，位于其同一 y、`x=cube_hi_x+1,z=0` 的外露地面点距离至多 `118.90016820845966 m`，因此远处侧面和底面不可能成为最近边界。

在原逻辑地图的自由空间，距离等于 `min(原柱盒的解析外部距离, z)`，保留原有限地面的查询含义。在柱子内部，采用“柱子与地下实体的并集”定义；柱底成为内部面并被消除。例如接地柱内 `z=0` 的点可能有负距离，不能再把开放地面的零距离当作并集距离。逻辑域外的扩展地面是明示的模型选择，不宣称与原有限薄片等价。

| 独立检查 | 结果 |
|---|---|
| 外露矩形／导出顶点／三角面 | 5618／14814／29624 |
| 网格无向边 | 44436；每条边恰出现两次且方向相反，坏边 0 |

边配对和非退化检查支持当前资产的闭合导出，不是任意输入的自交、顶点邻域拓扑或最近三角形算法正确性证明。合法的钝角三角形仍可能触发底层查询算法错误；“没有退化面”不能替代距离检查。

## 距离 oracle 的独立依据

`distance_numpy` 与 `distance_torch` 都以 float64 计算点到每个外露矩形的解析距离，再由原始盒及 slab 的占据并集给符号。Torch 路径保持输入设备并显式 `no_grad`；它只用于独立数值观察，不是训练反传后端。矩形构造与导出 mesh 共享几何预处理，因此还做了以下解析及三角面枚举对照，避免只验证两份共享错误的结果。

| 检查 | 结果 |
|---|---|
| 单盒与解析 SDF | 最大误差 `2.22e-16 m` |
| 两个贴合盒的并集与单个大盒解析 SDF | 最大误差 `4.44e-16 m` |
| 共面部分重叠双盒的并集表面积 | `38 m²`；重复完整盒只保留六个外露面 |
| 十字交叠双盒中心 | `-sqrt(0.08)=-0.28284271247461906 m`，不是逐盒 SDF 最小值 `-0.2 m` |
| 柱 `[-1,1]²×[0,2]` 与地下 slab，查询 `(0,0,0)`、`(0,0,0.1)` | 均为 `-1 m`，正确删除内部柱底面 |
| 原地图 1548 个自由点，与独立 `min(500盒解析外部距离,z)` 比较 | 最大误差 `1.78e-15 m` |
| 52 对正体积重叠的中心 | 全部为负距离 |
| NumPy／Torch CPU，不同分块边界 | 最大差 `4.44e-16 m`；输出无 autograd 图 |
| 空数组及 NaN／±Inf 查询 | 空形状保留；非有限查询返回 NaN |

自由点来自固定 seed `741` 在整个逻辑域采样的 1600 点，先用独立解析盒占据排除内部点。解析用例、分块对照、导出计数及源文件覆盖保护均在 Docker CPU 中执行。这里没有声称穷尽所有空间点，也没有验证 Torch GPU oracle 的本机执行性能。

另外读取 `real-map-20261017/roi-adaptive-evaluation.json` 保留的最坏 12 点，重新解析磁盘 `union.obj`，在 float64 下穷举全部三角面：用平面投影及重心条件检查面内候选，再检查三条夹紧线段候选。12 点均与矩形 oracle 的 unsigned 距离相差 `<1e-12 m`，且占据符号、最近点沿外法向两侧的占据关系均正确。磁盘顶点和三角索引与适配器输出逐项相等。

其中最坏点 `(2.2943529276689634,1.2560906879737153,0.004218114497394696)` 仅在柱 242 内。最近点为 `(2.3780330085230643,1.2560906879737153,0.004218114497394696)`，位于外露 `+x` 侧面；真实 SDF 为 `-0.08368008085410095 m`。最近三角形编号 7052，重心坐标约 `(0.00282509,0.89753994,0.09963497)`，`|cross|/max_edge²=0.53759`。第二个最坏点位于柱 127，真实 SDF 为 `-0.06119253422282789 m`，最近三角形 3593 的同一质量指标为 `0.15511`。这排除了这些查询点的矩形 oracle、未删内部柱底面或最近三角形退化造成约半米偏差的解释；不能仅凭这些点确定场构造中出错的具体分支。

## 导出、训练接线与审查边界

只读核对了 `export_sdflib.cpp` 与 `sparse_field.py`：C++ 将叶子的整数深度坐标转为 Morton 前缀区间，Python 使用相同的 x/y/z 位序及右侧二分查找。导出与读取均检查完整 cube 区间分割；读取还校验叶编号排列、深度、尺寸和原点。节点／叶编号独立存为整数，避开旧 float32 编号的 `2^24` 限制。逻辑查询域与定位用 cube 分开，未建立最细层稠密三维索引表。

这部分是源码审查，另读取了 research 已保存的 `cpu-sparse-20261017/cpu-parity.json`、`translated-parity.json` 与 `patch-check.json`，没有把它们标作本审查者重跑的结果。现存证据包括：小场 sparse／dense 的 39006 点叶编号、值和梯度一致；平移场 2048 点 native 对照的最大值差约 `3.85e-6 m`、原始梯度分量差约 `7.12e-6`，叶编号不一致为零。它们支持接口和世界坐标缩放，不证明实际全图所有接缝或真实几何梯度正确。

实际地图评估的 accuracy 查询使用原逻辑域；ROI 仍以完整 500 柱并集建场，不截走 ROI 外可能影响距离的障碍。优化器将 `d<0` 的中心进入实体、`d<0.2 m` 的球体半径违反、`d<0.3 m` 的安全距离违反分别统计。Bernstein 控制点包含检查是整条曲线留在查询域的充分条件；96 个训练采样及 513 个独立观察点并不构成连续避碰保证。参数有限差分验证场自身的反传，不等于真实并集几何梯度误差验证。

## 原始采样补丁的独立反例

`TriangleUtils`／tmd 原始采样与补丁由 research 实现和验证；另一位 review agent 编写、执行了独立探针。本节依据已读取的 `review-robust-primitive-20261017/check.py`、`v3/summary.json` 和配套 `raw.npz`，明确区分于前面的本审查者执行结果。

最初直接用 tmd 返回的 signed distance 和 nearest point 计算 `(p-q)/d` 的 robust v3，能通过原有 612 点，但未通过新增地面近零距离检查。新增检查用 seed `812` 在原逻辑 XY 域的 `0.0125 m` 格点上抽取 1024 点，解析筛选出距任何柱体水平投影大于 `0.05 m` 的 939 个不同位置；这些位置的平坦地面真值为 `d=z, grad=(0,0,1)`，包括 `z=0`，没有几何中轴或法线不唯一问题。七个高度分别启动新进程，避免诊断用的近表面点被共享节点缓存当作同一个逻辑格点。

| v3 检查组 | 点数 | 梯度分量误差 `>0.01` 的点数 | 最大梯度分量误差 |
|---|---:|---:|---:|
| `z=0` | 939 | 142 | `1.0391022` |
| `z=±1e-7 m`，分别统计 | 各 939 | 各 469 | `1.0391022` |
| `z=±1e-5 m`，分别统计 | 各 939 | 各 10 | `0.5196162` |
| `z=±0.0125 m`，分别统计 | 各 939 | 各 0 | `0.000485533` |
| 原有 612 点 | 612 | 0 | `5.78371e-7` |

例如 `p=(-10.1875,14.462499618530273,0)` 的真实距离为零，真实梯度向上；v3 得到约 `6.031566e-6 m`，梯度约 `(-2.64e-5,1.00623,0)`。记录中的最近点有约 `6.07 µm` 的切向偏移，除以近零距离后放大为明显错误的方向。此反例说明微米级值误差仍可破坏 Hermite 梯度，不能因距离值小或旧 612 点通过就认可原始梯度。

该 v3 失败证据对应探针二进制 SHA-256 `8d47d894e92247f048706b6d6adfeebd55dceb2a0541cb0d7ecafcee1063f2e7`，测试脚本 SHA-256 `5e6db49f07a76cf196bb421bffb8c4a4602f6cc9d90f21d362298e5625209796`，输入 union mesh 哈希与本报告首表一致。检查容差为距离 `1e-5 m`、唯一梯度分量 `1e-3`；表中的 `0.01` 只是另列的明显误差计数阈值。地下探针验证的是明示扩展 slab，不是原开放地面的新观测。

v4 保留 tmd 的选面及边／顶点符号信息，用所选三角形的平面投影和三条夹紧线段重新计算最近点与距离幅值，避免直接使用前述有消减误差的距离／最近点。另一位 review agent 随后用**同一脚本、点集与阈值**独立重跑，结果保存在 `review-robust-primitive-20261017/v4/summary.json` 和 `raw.npz`，本审查已读取核对：

| v4 独立检查 | 距离最大绝对误差 | 唯一梯度最大分量误差 | 结果 |
|---|---:|---:|---|
| 939 个地面 XY × 七个高度，共 6573 点 | `0` | `0` | 与实际 float32 输入位置上的解析地面值逐项一致 |
| 原有 612 点 | `3.2419689244278516e-7 m` | `5.783708552087319e-7` | 通过相同容差 |

这组 v4 证据的探针二进制 SHA-256 为 `35e6a25b4ad1e683d7d86f0823d304ec5443bc21e203843531b3cb5581dd7547`；`nodal_patch.py` 为 `06d4108830b5e618a30734fb3b0a9847d26fc9eee600dbc2c7dfbab102f8dadb`；生成的插值头文件为 `29aba8b4a8708be7a5e581d0d487a725f371dbf2e9664a0d45d6549b1677e4a7`。探针脚本和输入 mesh 哈希与 v3 对照相同。

## 全图构建资源与地址上限

两个 v4 全图 `start_depth=3,max_depth=12`、最细 `0.025 m` 的运行均未完成，且各自有同一容器的明确 Docker `oom` 事件，不是仅凭退出码推断：

| 全图终止参数／产物目录 | 内存／内存加 swap 配额 | 导出器运行时间及结果 | OOM 证据 |
|---|---|---|---|
| `1 mm`／`real-map-stable-20261017` | `12 GiB / 14 GiB` | `1756.033214705 s`，约 `29.27 min`，子进程 `-9` | `full.build-process.json`、`full.oom-events.jsonl` |
| `2 mm`／`real-map-full2mm-20261017` | 初始 `12 GiB / 14 GiB`，构建途中增至 `14 GiB / 20 GiB` | `1629.357906095 s`，约 `27.16 min`，子进程 `-9` | `full.build-process.json`、`full-build-docker-events.jsonl` |

第二次运行的 `hardware-context.json` 记录配额变化，构建中 `full-build-resource-snapshot.json` 还实际读取到 cgroup 的 `memory.max=15032385536`、`memory.swap.max=6442450944` 字节，与 `14 GiB` 内存加 `6 GiB` swap 一致；后续 Docker 事件确认该容器发生 OOM。两次都没有完整全图导出元数据或叶数可供审查，不能写成 `0.025 m` 全图建场成功。保留的内存样本不保证最终峰值；第二次同时改变了终止参数和资源配额，也不能把运行时间差只归因于误差参数。

以下为 research 提供、且本审查只读核对固定上游源码的资源解释，**字节数是常见 64 位 ABI 下的静态布局估计，不是分配器或峰值实测**：

| 对象与生命周期 | 源码所支持的资源边界 |
|---|---|
| `OctreeSdfBreadthFirstNoDelay.h` 的 `NodeInfo` | 包含 27×8 项原始 Hermite float、64 项系数、27 个面索引及邻居／容器成员，约 `1320 B/节点`，尚不含各三角索引 vector 的动态缓冲区。 |
| 同构建函数的 `nodesBuffer`／`leavesData` | 按深度保留 NodeInfo vectors；末尾的旧 buffer 清理代码被注释，叶映射也未逐项释放，直到函数退出。不能只按最终叶子系数估算建场内存。 |
| 节点共享补丁的两个 static map | 原始 Hermite 与首次位置合计约 `160 B/唯一采样点`，未含分配器额外开销；保留至进程退出，因此还与后续导出阶段重叠。 |
| 导出阶段 | `Leaf` 约 `292 B/叶`，收集 vector 会扩容；Morton 临时区间约 `24 B/叶`；另有 node→row 映射。Morton 临时数组只在其函数内存在，不应把不同阶段所有容器容量机械相加为峰值。 |

当前 CONTINUITY 因 `DELAY_NODE_TERMINATION=false` 进入上述 NoDelay 构建路径。另一个独立限制来自 `OctreeSdf.h`：索引只保留低 30 位，`setValues` 会掩去更高位。其可寻址跨度是 `2^30` 个四字节树存储 word，即 `4 GiB`；这不是整个进程可用内存上限。导出器中的 `data.size()>2^30` 检查发生在构造完成之后；上游在此之前已遍历树并调用 `computeMinBorderValue()`，所以该检查不能保护构建过程免于索引截断。

两次都没有最终 `tree_storage_words`，**不能由 RSS、容器配额或 OOM 反推是否触及 30 位索引上限**。确认的事实是上述两次受限配置 OOM；源码分析解释了为何建场占用可能远大于最终树，并揭示另一个尚需单独计数检查的地址限制。
