# 算法

`tof_tracker` 是最终交付算法的源码边界：模型及其输入适配、末状态选取和判断逻辑。当前 `observation.py` 只有职责占位，没有可调用的观测适配或模型接口。以下是当前输入输出约定，不代表已实现接口。

## 位姿工具

[`geometry.py`](geometry.py) 提供 NumPy CPU 版刚体 `Transform`，支持 `(..., 4, 4)` 批量矩阵和广播。`T_A_B` 的源为 A、目标为 B；点变换带平移，矢量变换只旋转。

在开发容器中使用：

```python
from tof_tracker.geometry import Transform

T_A_B = Transform.from_quaternion("A", "B", [1, 2, 3], [0, 0, 0, 1])
p_B = T_A_B.apply_points([1, 0, 0])   # [2, 2, 3]
v_B = T_A_B.apply_vectors([1, 0, 0])  # [1, 0, 0]
T_B_A = T_A_B.inverse()
```

组合使用 `T_B_C @ T_A_B`，帧标签不匹配会报错。不同时刻的本体系需用不同标签（如 `B_i`、`B_j`）；工具不自动补偿时间或计算相对运动。输入限于 NumPy 数组和 Python 列表/元组，不隐式转换其他张量后端。完整参数约定见源码；验证入口为 [verify_geometry.py](../../tests/verify_geometry.py)，由 `just check` 运行。

## 输入约定

三维状态以 `B_ref = B(t_ref)`，即测量参考时刻的真实本体 FLU 表达：X 向前、Y 向左、Z 向上。保留完整三维姿态与 Z 分量；本体 Z 不要求与世界 Z 对齐，不将观测回正到水平系。ToF 距离和图像提示按下述通道、像素语义解释。

| 字段 | 含义 |
|---|---|
| `t_ref` | 测量参考时间；算法结果关联并回传该时间 |
| `tof_m` | 四路 8×8 米制距离，包顺序为右、前、左、后 |
| `state_b` | 本体平移速度和加速度，顺序为 `vx, vy, vz, ax, ay, az` |
| `target_hint` | 观测置信度和四个归一化框边界，共五个数 |

每路 ToF 按 `row * 8 + col` 展开，行向下、列向右。若复用旧 Omni 模型的前、左、右、后布局，由算法适配层显式重排；新模型布局在实现时明确。模型归一化也由适配层处理。

`state_b` 中的加速度是平移加速度，静止时为零，不能直接使用含重力的原始 IMU 读数。

目标提示为：

```text
[confidence, u_min/W, v_min/H, u_max_exclusive/W, v_max_exclusive/H]
```

像素框使用半开边界 `[u_min, u_max_exclusive)`、`[v_min, v_max_exclusive)`，再按图像宽 W、高 H 归一化。未检出时为五个零。置信度支持 `[0, 1]`，几何核查阶段可产生 0/1；它与后续算法输出的方位置信度含义不同。

## 系统供给前提

以下是算法要求系统提供的接入条件，联调和故障排查时应逐项核对；记录这些条件不代表目标系统已经确认或验证满足。

| 前提 | 排查时核对 |
|---|---|
| 系统负责设备标定、安装外参和坐标适配；三维状态和几何量按 `B_ref` 解释，算法不再校正设备原生坐标 | 本体参考点、轴向与单位是否一致，是否回正到水平系或发生重复坐标转换 |
| 系统负责观测与状态的时间配对，提供可追溯的 `t_ref`；算法结果仍关联原参考时间 | 各路测量时间、组包策略及结果关联时间，不能用推理完成时间代替测量时间 |
| 系统提供上文定义的平移运动状态，而非未经处理的 IMU 读数 | 速度与加速度的表达系、单位和估计量含义；静止加速度是否为零 |
| 系统按本页格式交付观测，明确缺失、无效和超量程数据的含义 | ToF 通道与像素布局、目标提示有效性及无返回编码；最大量程值不能直接当作已确认空闲 |
| 系统维护参考时刻的世界位姿，负责轨迹重建、坐标转换、采用与执行；轨迹仍以 `B_ref` 表达 | 轨迹与参考位姿是否配对，实际执行起点、延迟及既有轨迹衔接是否被正确处理 |
| 系统负责实际权限、制动和位置/航向保持，独立决定接管与恢复 | 实际控制模式和停稳情况；算法接管请求不等于已经切权或停稳 |

仍需与系统明确：时钟域和同步容差，缺帧、过期、无返回与异常输入的处理规则，以及推理/执行延迟下的轨迹采用策略。旧稿中“低速时延迟影响可近似忽略”是未验证的阶段假设，不作为本项目保证。

职责依据为邻仓 `yopo_tracker_ws/docs/tracking-algorithm-system-agreement-v0.1.md`；设备坐标适配归系统是本项目进一步明确的前提。具体数据布局以本页为准，不沿用旧工程的无效值编码或消息 ABI。

## 输出目标与运行边界

开发目标包括接近目标、避障、主动调整航向和提前减速。输出目标是终点状态 `(p, v, a, yaw, vyaw)`、目标三维方位与置信度，以及稳定的 0/1 接管请求；`vyaw` 表示终点航向角速度。实际轨迹解析、坐标转换与执行由系统负责；训练和开发评价调用 [devtools 的轨迹解析工具](../../devtools/README.md#开发用轨迹解析)。上述算法输出与判断能力尚未实现；网络结构、候选生成、近距监督和滤波方法尚未确定。

世界位姿、目标真值和物体身份用于开发工具、监督与评价，不得补入在线观测。在线算法核心不导入 `training` 或 `devtools`，不加载地图或仿真器。开发观测与几何能力见 [devtools](../../devtools/README.md)，训练组织见 [training](../../training/README.md)。

研发与训练以 Python 为主；需要部署的算法工程部分采用可在 C++ 中运行的实现，交付运行路径不要求 Python。模型形成稳定的完整前向后，在大量训练前与系统侧检查目标工具链转换能力；实际平台部署由系统侧负责。
